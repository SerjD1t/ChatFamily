# Резервные копии ChatFamily

Статус на 2026-09-17: установлена и включена на VPS. Ежедневно в **02:30 Europe/Moscow**,
прогрессивное хранение 2/30/90/365 дней, лимит 450 ГиБ. Первая зашифрованная копия
создана; восстановление PostgreSQL и originals в изолированном контейнере прошло.
Повторный запуск через systemd с рабочими лимитами ресурсов также прошёл; две
точки занимают суммарно около 20 МБ благодаря дедупликации. Это проверка установки,
а не подтверждение будущих запусков: нужен внешний мониторинг пропущенных копий.
Фиксированное ежедневное время и поддержка старых имён файлов добавлены после v0.11.0.

Проверено 2026-09-17: Go-тесты/сборка, 42 web-теста без пропусков, 15 Python-тестов
с настоящим restic roundtrip на синтетических данных. Облачный smoke прошёл
init → backup → check --read-data → restore с побайтным сравнением через ограниченный
токен; все созданные тестовые репозитории удалены. Снимок рабочего Docker/PostgreSQL
и тест PostgreSQL-восстановления на VPS прошли. Визуальная приёмка на физических
Android/Safari и фактический первый ночной запуск остаются ручными проверками.

## Что реализовано

- Раздел «Администрирование приложения → Резервные копии», только manage_application.
- Настройка включения, интервала 1/3/6/12/24 часа либо ежедневного времени HH:MM, часового пояса расписания/группировки,
  возрастных границ хранения и лимита репозитория до 500 ГиБ.
- Проверка подключения, ручной запуск с предупреждением о короткой паузе чата,
  статус/очередь, последняя успешная копия, точки восстановления, журнал 100 операций
  (в интерфейсе последние 20), дата проверки восстановления БД.
- Отдельный Python worker под systemd, не зависящий от процесса чата. Таймер проверяет
  расписание каждую календарную минуту. Поле `dailyTime` задаёт ежедневное время
  в указанном часовом поясе и имеет приоритет над интервалом; пустое поле сохраняет
  интервальный режим. Ручная копия не сдвигает час расписания. После пропуска
  сегодняшнего запуска выполняется одна догоняющая копия; до сегодняшнего часа
  запуска служба ждёт его. Ошибка повторяется не чаще 30 минут. Из-за нагрузки или
  недоступности VPS фактический старт может запоздать.
- restic 0.19.1: шифрование до отправки, дедупликация неизменившихся блоков, проверка
  репозитория. Никакого зеркального sync рабочей папки поверх резервных копий.
- Яндекс Диск: только `cloud_api:disk.app_folder`, фиксированный репозиторий
  `app:/chatfamily-restic-v1`. Адаптер проверяет доступ к app:/ и отказ для disk:/.
  Полный доступ к Диску отвергается. Удаление корня репозитория адаптером запрещено.
- Чтение квоты всего Диска не требуется: считается объём объектов нашего репозитория.
  Лимит консервативный (повторная запись может временно завысить оценку до следующего
  инвентаризирования). Он не гарантирует доступность места, занятого другими файлами
  аккаунта: ответ облака о нехватке места приводит к ошибке, а не досрочной очистке.

## Хранение: прогрессивная схема

Возрастные диапазоны не пересекаются. В каждом календарном периоде сохраняется
самая поздняя копия; часовой пояс задаётся явно.

| Возраст | По умолчанию |
| --- | --- |
| Менее 2 суток | Все |
| От 2 до 30 суток | Одна в день |
| От 30 до 90 суток | Одна в ISO-неделю |
| От 90 до 365 суток | Одна в месяц |
| От 365 суток | Одна за календарный год, без предельного возраста |

Последняя точка всегда сохраняется. Forget/prune запускаются только после новой
успешной копии и проверки. Если копирование не удалось, старые точки не удаляются.
При превышении лимита сроки сами не сокращаются: нужны решение администратора и
место для нового запуска. При prune удаляются только конкретные устаревшие ID и
неиспользуемые блоки выделенного репозитория, не файлы вне него и не корзина Диска.
Удалённые облачные блоки не перемещаются в корзину; это окончательное удаление
по политике, а не удаление рабочих данных. Репозиторий нельзя редактировать вручную.

## Согласованность и состав

1. Проверяются облако и существующий репозиторий; автоматической переинициализации нет.
   `restic unlock` снимает только устаревшие блокировки после сбоя, не активные.
2. Записывается маркер возобновления. Останавливается только app (если он работал).
3. Создаётся `pg_dump -Fc` PostgreSQL, проверяется `pg_restore --list`.
4. В закрытый временный каталог копируются оригиналы вложений/аватары, параметры
   запуска, бинарник и web из работающей версии контейнера, manifest с образом и датой.
5. В finally запускается app. Только затем данные шифруются restic и отправляются.
6. Проверяется структура репозитория и читается/расшифровывается 5% данных.
7. Применяется ротация, обновляется список точек, временный снимок удаляется.

systemd ExecStopPost повторяет возобновление при аварийном завершении процесса.
На следующем запуске worker удаляет только собственные остатки временного снимка.
Все обычные файлы в корне originals сохраняются, включая старые имена не в формате
hex ID. Неожиданные подкаталоги и симлинки прерывают копирование, а не молча теряются.
В БД не должно быть других писателей во время снимка — остановка app не блокирует
ручные SQL-записи внешнего оператора. На время копии не проводить обслуживание БД.

Не сохраняются регенерируемые миниатюры и карантин неподключённых файлов.
`settings.local.json`, токен Диска и пароль restic **не входят** в саму копию:
они нужны для доступа к ней и должны иметь отдельную защищённую аварийную копию.
В аварийном комплекте вне VPS сохранить также код адаптера/worker и эту инструкцию:
для чтения репозитория restic потребуется адаптер к app:/.
Персональное оформление из localStorage/кэш телефона не входят в серверный backup.

Снимок требует места под оригиналы, оценку размера БД, приложение плюс резерв 1 ГиБ. Длительность
паузы растёт с размером файлов; текущая реализация предназначена для малого сервера.
На Linux локальный снимок ограничен 180 секундами: при превышении он отменяется,
чат возобновляется; проверка health может занять дополнительное время.
До включения измерить паузу на реальном объёме. При росте перейти на файловые
снимки/согласование записей, а не увеличивать паузу без предупреждения.

## Секреты и подключение

Единственный локальный файл — корневой settings.local.json, исключённый из Git и
Docker-контекста. Worker понимает ровно один объект `yandexDiskBackup` как в корне,
так и во вложенном объекте существующих настроек. Несколько таких разделов — ошибка.

Поля объекта (значения секретов не вставлять в команды, переписку, логи или Git):

- `accessToken` — уже полученный ограниченный токен;
- `repositoryPassword` — отдельный случайный пароль шифрования, не менее 24 символов;
  создать в менеджере паролей и сохранить независимую аварийную копию ДО init;
- `appContainer`, `postgresContainer`, `deploymentDirectory` — необязательные
  параметры оператора; defaults соответствуют текущим именам проекта;
- `alertWebhookUrl` — необязательный HTTPS endpoint внешнего мониторинга. Получает
  POST JSON: service, action, ok, at; ни текст переписки, ни ошибки с секретами не отправляются.

Не менять repositoryPassword после init без отдельной процедуры `restic key`!
Простая замена лишит worker доступа. Токен можно заменять, сохраняя то же OAuth-
приложение (app:/ связан с ним), аккаунт и пароль репозитория.
Ручной access token не обещается бессрочным: при истечении/отзыве копирование
останавливается и показывает ошибку. Автоматическое OAuth-продление пока не реализовано.
Нормальные запуски не используют браузер и не требуют участия оператора.

Облачный адаптер `yandex_rest.py` реализует REST v2 restic, слушает только случайный
loopback-порт с одноразовым паролем. OAuth остаётся в памяти адаптера; restic видит
лишь локальный URL. Облачные подписанные ссылки принимаются только по HTTPS на
поддоменах Яндекса; каждый редирект проверяется, OAuth на них не передаётся.
Веб-приложение не получает Docker socket, облачные ключи, пароль шифрования или архив.

Основа: [REST backend restic](https://github.com/restic/restic/blob/master/doc/REST_backend.rst).
Rclone не используется: ограниченная папка добавлена в него недавно, а его клиент
требует refresh token; текущий ручной токен проверяется напрямую через API Диска.

## Установка на VPS — отдельное согласованное развёртывание

Не выполнять эти шаги как часть обычного просмотра документации.

1. Проверить актуальный хост, SSH-ключ, место/память; сохранить действующие данные.
2. Установить Python 3.10+ с системной tzdata и официальный restic 0.19.1, сверив
   SHA256 релизного файла. На VPS ничего не компилировать.
3. Разместить `deploy/backup/worker.py`, `yandex_rest.py` под `/opt/chatfamily/deploy/backup`
   и `deploy/Dockerfile.runtime` под `/opt/chatfamily/deploy/Dockerfile.runtime`.
4. Без вывода значений подготовить `/opt/chatfamily/settings.local.json` с секретами
   бэкапа; root:root, 0600. Он не монтируется в app и не копируется в образ.
   Старый bind mount этого файла для Firebase необходимо убрать. На текущем VPS
   `FCM_SERVICE_ACCOUNT_JSON` подставляется из памяти через `deploy/compose.py`;
   в контейнер передаётся только firebase.serviceAccount, не весь файл. Секреты
   бэкапа недоступны app. Docker-администратор по-прежнему имеет доступ к env FCM.
5. Создать `/var/lib/chatfamily-backup/runtime` root:root 0700 и
   `/var/lib/chatfamily-backup/control` root:группа-контейнера 2770. Проверить реальный
   GID пользователя app (`id -g` в контейнере), не предполагать его по памяти.
   Status-файлы worker: 0640, группа наследуется от каталога. Policy пишет app: 0600.
6. Подключить `deploy/backup/compose.backup.yml` последним override к текущему Compose.
   Сохранить этот override в последующих деплоях. Проверить чтение status и запись
   policy от пользователя контейнера, не делать каталог 0777.
   Текущая команда запуска: `python3 deploy/compose.py up -d --no-build --no-deps app`
   из `/opt/chatfamily`. Обёртка сохраняет override и передаёт Firebase из защищённого
   settings.local.json. Прямой Compose без этой переменной намеренно отклоняется;
   не выводить `docker compose config`, он может раскрыть настройки окружения.
7. Выполнить `python3 /opt/chatfamily/deploy/backup/worker.py check`, затем **один раз**
   `.../worker.py init`. Init не включается в таймер, не перезаписывает репозиторий.
8. Установить unit-файлы в `/etc/systemd/system`, daemon-reload, enable --now
   chatfamily-backup.timer. По умолчанию автокопирование выключено.
9. Ручной `.../worker.py run`, затем `.../worker.py restore-check`. Измерить паузу,
   проверить health, приложение, память, снимок и восстановление. Сохранить ключ отдельно.
10. Включить расписание через админку, настроить внешний мониторинг пропущенного
    сигнала. Без внешнего наблюдателя остановка самого VPS не может породить уведомление.

Только кнопка «Проверить подключение» не доказывает работоспособность записи,
шифрования, ротации и восстановления. Готовность репозитория не заменяет эти шаги.

## Проверка восстановления и аварийное восстановление

- `worker.py verify`: полное чтение и проверка всех облачных блоков.
- `worker.py restore-check`: загрузка последней копии в новый временный каталог,
  restic restore --verify, проверка количества/размера originals, восстановление
  dump в отдельный PostgreSQL-контейнер **без сети/портов**, проверка таблиц и наличия
  вложений/аватаров по ссылкам БД. Контейнер и временные файлы удаляются после теста.
- Такой тест выполняется после первой автоматической успешной копии и затем раз
  в 30 дней; неудачный тест повторяется не чаще суток. Он не запускает веб-приложение
  и не отправляет push пользователям. Отдельная функциональная приёмка всё ещё нужна.
- Тестовый PostgreSQL ограничен 256 MiB RAM и 192 MiB tmpfs. При росте БД тест может
  перестать проходить: перенести проверку на отдельный хост или пересмотреть лимит,
  не снимать ограничения без оценки ресурсов. Прерванный тест очищается по точному ID
  с обязательной проверкой метки контейнера; рабочий PostgreSQL не затрагивается.
- Для реальной аварии: остановить таймер, подготовить новый сервер и независимые
  credentials. Команда `worker.py export --target /opt/chatfamily-restore-YYYYMMDD`
  расшифровывает последнюю точку только в **новый** каталог. Существующий путь запрещён.
  При ошибке каталог сохраняется для анализа, не объявляется успешным восстановлением.
- Из экспортированных application/ восстановить runtime (нужны FFmpeg/Poppler/prlimit),
  из launch/ — проверить Compose/окружение, из database.dump — восстановить в новую
  БД, originals — в новый том uploads. Сверить владельцев/права и настройки домена.
  Сначала изолированная приёмка, затем переключение. Не восстанавливать дамп поверх
  работающей БД и новых сообщений без отдельного решения о потере более свежих данных.

## Проверки разработки

```text
go test ./...
node --check web/backup-admin.js
node --test web/*.test.mjs
python -m unittest discover -s deploy/backup -p "test_*.py" -v
```

Для DOM нужен TEST_JSDOM_PATH. Для полного Python roundtrip — RESTIC_TEST_BIN,
для Windows дополнительно tzdata в тестовом окружении. Без RESTIC_TEST_BIN один
integration-тест пропускается, что не считается проверенным roundtrip.

`smoke_yandex.py --settings settings.local.json --restic <путь>` — явный облачный
тест только синтетического файла: создаёт уникальный app:/chatfamily-smoke-* repo,
проверяет шифрование/восстановление и удаляет только свои тестовые объекты.
Рабочий chatfamily-restic-v1 не используется. Проверять итог cleanup.

Новый APK для административного интерфейса не нужен. Git push, релиз и установка
на сервер — отдельные действия. Наличие локальных unit-файлов не означает работу таймера.
