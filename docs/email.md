# Почта, подтверждение регистрации и восстановление пароля

Установлено на сервере 2026-09-21 после v0.13.0, миграция **032**.
SMTP-контроллер работает; отправка и подтверждение регистрации выключены до настройки
и успешного теста администратором. Реальная доставка ещё не проверена.

## Пользовательские сценарии

- На входе — «Забыли пароль?». Ответ одинаков для существующего, неизвестного
  и отключённого аккаунта. Ссылка действует 30 минут и используется один раз.
- После включения подтверждения регистрация отправляет письмо, но ещё не создаёт
  пользователя. По ссылке человек задаёт пароль и подтверждает адрес; только тогда
  создаётся аккаунт. Ссылка действует 24 часа. Повторный запрос — не чаще раза в минуту;
  действует последняя выданная ссылка. Если письма нет, проверить спам и повторить запрос.
- Регистрация по приглашению проходит ту же проверку: письмо уходит на адрес
  приглашения, а аккаунт и членство создаются одной транзакцией. Входящий код сам
  по себе не обходит подтверждение при включённой политике.
- Существующих пользователей обязательная проверка не блокирует. Присоединение
  уже зарегистрированного пользователя по коду сохраняется.
- После сброса старые сессии и push-подписки отзываются. Приходит отдельное уведомление
  об изменении пароля, без самого пароля. Затем нужно войти заново; автоматического
  входа по ссылке нет. SMTP-ошибка уведомления не откатывает уже выполненный сброс.
- Смена пароля из своего профиля также отзывает старые сессии, сохраняя новую сессию
  текущего браузера. После установки пароля администратора bootstrap-пароль больше
  не является запасным способом входа.

Токены криптографически случайные; в БД хранятся только SHA-256, назначение,
срок и необходимые данные регистрации. Токен передаётся во fragment ссылки,
не в query: не попадает в обычный access log/Referer. Страница удаляет fragment
и выполняет действие только после явного подтверждения. Повтор, истечение,
отключение аккаунта и смена пароля между запросом и подтверждением проверяются
на сервере. Для нового пароля действует общая политика и ограничение bcrypt 72 байта.

Ручная повторная отправка: после запроса регистрации, регистрации по приглашению
или восстановления кнопка меняется на «Отправить письмо повторно» с отсчётом
60 секунд. Поля сохраняются; повтор использует актуальные значения формы.
Повторные нажатия во время запроса блокируются, при явной ошибке API можно повторить
запрос. Серверное ограничение частоты действует независимо от интерфейса.
После закрытия страницы можно заново открыть соответствующую форму и запросить письмо.
Сохранения адреса, пароля или кода приглашения в browser storage для повтора нет.

По решению пользователя долговечная очередь и автоматические повторы не нужны.
Почтовые попытки ограничены по частоте и числу одновременно выполняемых операций.
Отправка асинхронна; при перезапуске приложения незавершённую попытку нужно запросить
повторно. Это не гарантированная очередь доставки. SMTP-принятие не доказывает
попадание во «Входящие». При неопределённом сетевом ответе ссылка остаётся действительной
до истечения срока, чтобы уже доставленное письмо не стало бесполезным.

## Настройки администратора

Администрирование приложения → **Почта и подтверждения**. Доступ только
`manage_application`; семейные администраторы этих прав не получают.

1. Указать SMTP-хост, порт, STARTTLS либо TLS, логин, пароль и адрес отправителя.
2. Сначала сохранить с выключенными отправкой и подтверждением регистрации.
3. «Отправить тест мне» использует сохранённые настройки и почту текущего администратора.
4. Убедиться, что письмо пришло. Затем включить отправку/восстановление и при
   необходимости подтверждение регистрации. Без успешного SMTP-теста включение запрещено.
5. При смене подключения сначала отключить обе галочки; изменение параметров
   аннулирует результат старого теста. Пустой пароль сохраняет прежний, для удаления
   есть отдельная галочка. Сам пароль никогда не возвращается в API/форму.

Показываются результат теста и состояние последней отправки, но не адресаты,
тела писем или необработанные ответы SMTP. Подключения без TLS/STARTTLS и отключение
проверки сертификата не поддерживаются. Существующие приглашения используют ту же
почту; legacy `MAIL_*` остаётся только для приглашений без нового сервиса, с обязательным TLS.

## Установка на VPS (по отдельному запросу)

Секреты хранятся **только в корневом `settings.local.json`**, в блоке `mail`.
Файл не монтируется в приложение: отдельный host-only сервис
`deploy/mail/service.py` предоставляет Unix socket, без TCP-порта.
HTTP API приложения проверяет права и обращается к этому socket. Сервис возвращает
только несекретные параметры/признак наличия пароля; другие блоки файла недоступны через API.

Перед обновлением: резервная копия БД/вложений, сохранение образа, проверка целевого
хоста. Сборка Go выполняется локально. Помимо бинарника и `web/`, перенести
`deploy/mail/`, обновлённые `deploy/compose.py` и `deploy/backup/worker.py`.

На текущей раскладке `/opt/chatfamily`:

```sh
chmod 600 /opt/chatfamily/settings.local.json
install -m 0644 deploy/mail/chatfamily-mail.service /etc/systemd/system/chatfamily-mail.service
systemctl daemon-reload
systemctl enable --now chatfamily-mail.service
python3 deploy/compose.py up -d --no-build --no-deps app
```

До установки проверить GID пользователя runtime-контейнера: unit использует 1000,
он должен совпадать с группой приложения. Socket имеет 0660; не расширять до 0666.
Unit фиксирует каталог проекта, ограничивает запись файлом настроек и каталогом socket.
`MAIL_CONTROL_SOCKET` передаётся только через `deploy/mail/compose.mail.yml`.
Обёртка добавляет override по установленному unit, даже если сервис остановлен:
ошибка сервиса не должна незаметно выключать проверку новых регистраций.

Для ссылок требуется корректный `APP_PUBLIC_URL` с HTTPS. До установки сервиса
почтовая панель сообщает о недоступности; старый вход работает как прежде.
При установленном, но недоступном сервисе регистрация не обходит проверку.

Запись в единственный файл настроек выполняется под `flock`, без дополнительного
файла с секретами; обновлённые Compose/backup-reader используют shared lock.
Ручные параллельные редакторы должны быть исключены. В отличие от atomic rename,
in-place запись не защищает от обрыва питания посреди записи: перед обслуживанием
нужен операторский план восстановления защищённых настроек. Сервис не создаёт их копий.
Ключи бэкапа не меняются. Не откатывать бинарник к версии без проверки регистрации,
оставляя регистрацию открытой, если подтверждение уже обязательно.

## Проверки перед включением

- Реальная доставка тестового письма, подтверждения, приглашения, сброса и уведомления
  о смене пароля; проверить SMTP/TLS, отправителя и SPF/DKIM/DMARC у провайдера.
- Safari/Android: письмо открывает форму, пароль можно задать и затем войти.
- Повтор/истечение ссылки, неверный пароль, отключённый аккаунт, смена адресата,
  два одновременных подтверждения, отсутствие доступа к SMTP у обычного пользователя.
- Старый браузер и старое push-устройство после сброса больше не получают доступ.
- При остановленном mail-сервисе нет регистрации в обход подтверждения;
  резервные копии в 02:30 продолжают читать настройки.

Автотесты используют синтетические данные и отдельную PostgreSQL, не рабочую БД.
При общей тестовой БД запускать Go-пакеты последовательно (`go test -p 1 ./...`):
существующий механизм миграций не сериализует одновременно стартующие тестовые пакеты.
