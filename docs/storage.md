# Хранилище: настройки и обслуживание

Доработка после v0.10.0. Развёрнута 2026-09-16 в runtime chatfamily-app:20260916-storage без нового релиза.

Меню пользователя → «Администрирование приложения» → «Хранилище». Доступ только по глобальному праву `manage_application`, а не роли администратора семьи. API повторно проверяет право для статистики, настроек, анализа и выполнения.

## Что доступно

- Количество и суммарный объём оригиналов, миниатюр и карантина. Имена файлов и содержимое переписки не показываются.
- Наличие FFmpeg/Poppler/prlimit и текущий серверный лимит загрузки. Лимит загрузки показывается только для чтения: его изменение требует настройки сервера, а не формы.
- Включение миниатюр изображений, видео и PDF по отдельности. Оригиналы не меняются. Уже открытой странице после смены режима может потребоваться обновление.
- Пороги возраста: старый кэш (по умолчанию 30 дней, минимум 1), неиспользуемые загрузки (30, минимум 7), карантин (30, минимум 7). Верхняя граница 3650 дней. Это параметры ручных операций, не расписание автоудаления.
- Очистка всего кэша или только старого. Миниатюры создаются заново при запросе; возраст определяется временем создания, не последнего просмотра.
- Перемещение старых неиспользуемых загрузок в карантин. Файл не должен иметь ни одной ссылки в attachments или users.avatar_key, даже от удалённого сообщения/архивной беседы. Старый неотправленный черновик может потребовать повторного прикрепления.
- Восстановление карантина без перезаписи существующих оригиналов.
- Безвозвратная очистка файлов, выдержавших срок именно в карантине и по-прежнему не имеющих ссылок в БД. До этой операции нужна резервная копия.
- Последние 20 записей операций: начало/результат, время, действие, число и объём файлов. Без имён/содержимого файлов, секретов и персональных данных. Незавершённое «Начато» требует проверки статистики: процесс мог прерваться.

Карантин не освобождает диск — только переносит файлы внутри хранилища. Связанные с сообщениями оригиналы не удаляются по возрасту. Очистка диска сервера, Docker-образов и резервных копий сюда не включена.

## Безопасность операций

Сначала анализ, затем отдельное подтверждение количества/объёма. Одноразовый план действует 5 минут, привязан к администратору и ограничен 10 000 файлами. Перед выполнением повторно проверяются ссылки, возраст, размер и время изменения каждого кандидата; при изменении списка требуется новый анализ. Повтор одного плана не выполняет операцию заново.

Обрабатываются только распознаваемые обычные файлы. Символические ссылки и неизвестные каталоги не обходятся; рекурсивного удаления нет. Физический карантин: `uploads/.storage-trash`; восстановление возвращает исходный ключ. Миниатюры: `uploads/.previews-v1`. Эти каталоги не должны раздаваться статическим HTTP-сервером.

Блокировка обслуживания согласована с загрузкой/отправкой файлов, аватарами и выдачей миниатюр в одном процессе приложения. После помещения старой загрузки в карантин отправка сообщения проверяет наличие оригинала и предлагает прикрепить файл заново.

Текущая поддерживаемая топология — один процесс ChatFamily. Перед несколькими репликами или внешними обработчиками файлов нужна распределённая блокировка; ручные изменения файлов/БД во время обслуживания не поддерживаются. Перед обслуживанием рекомендуется резервная копия.

## Хранение и проверка

Настройки и журнал сохраняются в существующей application_settings (ключи storage_settings/storage_history). Новая миграция не нужна. Планы только в памяти, после перезапуска нужен повторный анализ.

API: GET `/api/v1/application/storage`, PUT `/settings`, POST `/plan`, POST `/execute` относительно `/api/v1/application/storage`.

Тесты: `go test ./...`, `go test -run TestStorage -v .`, JavaScript с jsdom. TestStorageAdministrationIntegration требует только отдельную одноразовую PostgreSQL через TEST_DATABASE_URL (не рабочую БД). Проверить фактическое сохранение настроек, привязку/одноразовость плана, отказ обычному и семейному администратору, карантин/восстановление и журнал. В Windows тест символической ссылки может пропускаться; перед переносом выполнить его в Linux.

Развёртывание — бинарник и web вместе. Для серверного раздела APK не требуется. При обновлении рабочие вложения не очищались; операции карантина/восстановления проверены на синтетических файлах и отдельной одноразовой БД. Linux-проверка символических ссылок пройдена.
